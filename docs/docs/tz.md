# Техническое задание
## Drillix — система AI-подбора компоновок низа бурильной колонны (КНБК)

**Версия:** 0.2
**Дата:** 29.09.2026
**Статус:** согласовано (модель данных, раздел 6); открытые вопросы — раздел 13

---

## 1. Общие сведения

### 1.1. Наименование
**Drillix** — веб-приложение (REST API) для AI-подбора КНБК.

### 1.2. Назначение
Приложение для работников буровых компаний нефтегазовой отрасли: принимает технологические
требования по секции бурения (в MVP — ручной ввод параметров; автоматическое извлечение
из файлов ТЗ — этап 3), предлагает рекомендуемую КНБК с обоснованием, выбирая оборудование
из справочника компании.

### 1.3. Пользователи
| Роль | Описание |
|---|---|
| Технолог по бурению | Основной пользователь: вводит данные, получает и проверяет рекомендации |
| Администратор | Управление пользователями и справочниками (этап 2) |

### 1.4. Важное ограничение
Приложение является вспомогательным инструментом и не заменяет квалифицированного
специалиста по бурению. Итоговая ответственность за выбор КНБК остаётся за ответственным
инженером / технологической службой.

## 2. Цели и задачи

### 2.1. Цель
Сократить время предварительного проектирования КНБК и использовать накопленный опыт
в виде типовых решений.

### 2.2. Задачи
1. Обеспечить ввод исходных данных ТЗ по секциям скважины.
2. Реализовать AI-генерацию рекомендуемых КНБК с обоснованием.
3. Обеспечить просмотр, редактирование и экспорт результатов.
4. Накапливать историю подборов.

## 3. Термины и сокращения

| Термин | Описание |
|---|---|
| КНБК | Компоновка низа бурильной колонны (BHA) |
| Шаблон КНБК | Заранее допустимый (типовой) вариант компоновки; в системе реализуется как Bha с заполненным названием (этап 2) |
| ТЗ | Техническое задание на бурение скважины |
| Секция | Интервал, бурящийся под конкретную обсадную колонну (направление, кондуктор, пилотная, техническая, эксплуатационная, хвостовик) |
| УБТ | Утяжелённые бурильные трубы |
| НУБТ | Немагнитные утяжелённые бурильные трубы |
| ВЗД | Винтовой забойный двигатель |
| Долото | Породоразрушающий инструмент |
| РУС | Роторная управляемая система |
| MWD | Телесистема — измерения в процессе бурения технологических параметров (зенитный угол, азимут, температура, давление, вибрации и т.д.) |
| LWD | Геофизические и петрофизические исследования пород в реальном времени: гамма-каротаж, сопротивление, плотность, пористость, нейтронные параметры и др. |
| LLM | Большая языковая модель |
| Bothub | Агрегатор доступа к LLM разных провайдеров по одному API-ключу (OpenAI-совместимый протокол) |

## 4. Описание процесса
1. Пользователь вводит данные ТЗ по секциям скважины.
2. Система формирует структурированный запрос к AI: параметры секции + релевантная
   часть справочника оборудования.
3. AI генерирует вариант(ы) КНБК с обоснованием выбора.
4. Система проверяет ответ (валидация) и сохраняет результат.
5. Технолог проверяет, корректирует и принимает решение.

## 5. Функциональные требования

### 5.1. FR-1. Скважины
- FR-1.1. Создание скважины: месторождение, номер скважины (строка: «123Г», «45-А»),
  тип (вертикальная / наклонно-направленная / горизонтальная / ЗБС), проектная глубина,
  дата начала бурения, дата окончания работ.
- FR-1.2. Редактирование и удаление скважин.

### 5.2. FR-2. Секции скважины
- FR-2.1. Добавление секции: тип (направление, кондуктор, пилотная, техническая,
  эксплуатационная, хвостовик — хвостовиков может быть несколько), интервал (от/до, м),
  диаметр долота (дробный, мм).
- FR-2.2. Параметры секции: условия бурения (горно-геологические условия и осложнения —
  АВПД, осыпи и т.п. — единое текстовое поле), задача по траектории (вертикальный
  участок / набор угла / стабилизация / сброс угла / коррекция), максимальный зенитный
  угол (отдельное число, °).
- FR-2.3. Валидация: забой больше кровли; интервалы секций одной скважины не
  пересекаются. Соответствие диаметра типу секции автоматически НЕ проверяется
  (нет справочника конструкций) — контролирует технолог.

### 5.3. FR-3. AI-подбор КНБК
- FR-3.1. Формирование промпта из параметров секции + релевантной части справочника
  (фильтр по диаметру).
- FR-3.2. Ответ LLM строго в формате JSON: последовательность элементов КНБК от долота
  вверх; каждый элемент — позиция справочника (equipmentId) либо свободное описание
  (если подходящей позиции нет) + текстовое обоснование.
- FR-3.3. Генерация альтернативного варианта по запросу.
- FR-3.4. Повторная генерация с уточнениями пользователя.
- FR-3.5. Предусловие генерации: в справочнике есть оборудование нужного диаметра
  (минимум — долото). Если нет — AI не вызывается (fail fast), пользователю сразу
  возвращается понятная ошибка. Без траты токенов и времени.
- FR-3.6. Валидация ответа: ответ — валидный JSON; все equipmentId существуют
  в справочнике; долото присутствует и стоит на позиции 1; у каждого элемента ровно
  один режим (ссылка на справочник ИЛИ свободное описание). Любая проверка не прошла —
  рекомендация не сохраняется, пользователю возвращается понятная ошибка.

### 5.4. FR-4. Работа с результатами
- Просмотр КНБК в виде таблицы/схемы компоновки (от долота вверх).
- Ручное редактирование (добавление/удаление/порядок элементов) — этап 2.
- Статусы: черновик → согласована → отклонена (полный цикл — этап 2; в MVP всё
  создаётся как черновик с пометкой «требует проверки технологом»).
- Экспорт в Excel / PDF (формат уточнить).

### 5.5. FR-5. Справочник оборудования
- FR-5.1. Хранение позиций: тип, название, диаметр, описание.
- FR-5.2. Просмотр справочника с фильтрацией по типу и диаметру.
- FR-5.3. При генерации в промпт передаётся оборудование, отфильтрованное
  по диаметру секции.
- FR-5.4. Управление справочником (CRUD, импорт) — этап 2; в MVP — начальное
  наполнение вручную/скриптом.

## 6. Модель данных

Состав модели — шесть сущностей. Каждая закрывает свою роль:

| Сущность | Роль | Аналогия |
|---|---|---|
| Well | Объект работ: скважина | дело в архиве |
| Section | Вход генерации: интервал + условия | задание на работу |
| Equipment | Ресурс: справочник оборудования | прайс-лист |
| Bha | Результат: компоновка (шапка) | смета |
| BhaElement | Результат: строки компоновки | строки сметы |
| BhaRecommendation | Обоснование: для какой секции, что и почему | пояснительная записка |

Цикл работы: вход (Section) + ресурс (Equipment) → результат (Bha + BhaElement)
+ обоснование (BhaRecommendation).

### 6.1. Well (скважина) — таблица `wells`

Учётная запись скважины — объект, ради которого всё затевается. В генерации напрямую
не участвует (промпт собирается из Section), но группирует секции и нужен для навигации
и истории.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | Long | авто | Идентификатор (PK), генерируется БД |
| `field` | String(255) | да | Месторождение |
| `wellNumber` | String(50) | да | Номер скважины. **Строка**, т.к. в номерах встречаются буквы («123Г», «45-А») |
| `wellType` | enum | да | VERTICAL / DIRECTIONAL / HORIZONTAL / SIDE_TRACK (ЗБС) |
| `projectDepth` | Integer | да | Проектная глубина, м |
| `drillingStartDate` | LocalDate | нет | Дата начала бурения. Nullable — скважину заводят в системе до начала работ |
| `completionDate` | LocalDate | нет | Дата окончания работ. Nullable — заполняется по факту |
| `createdAt` | LocalDateTime | авто | Дата создания записи **в системе** (не дата начала бурения!), заполняется автоматически |

Валидация: `completionDate` не раньше `drillingStartDate` (если обе указаны).

### 6.2. Section (секция) — таблица `sections`

Интервал скважины под конкретную обсадную колонну. **Главный вход генерации**: из полей
секции собирается промпт.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | Long | авто | Идентификатор |
| `wellId` | Long, FK → `wells.id` | да | Скважина, к которой относится секция |
| `type` | enum | да | DIRECTION (направление) / CONDUCTOR (кондуктор) / PILOT (пилотная — не на каждой скважине) / TECHNICAL (техническая) / PRODUCTION (эксплуатационная) / LINER (хвостовик — может быть несколько) |
| `depthFrom` | Integer | да | Кровля интервала, м |
| `depthTo` | Integer | да | Забой интервала, м |
| `bitDiameter` | BigDecimal | да | Диаметр долота, мм. **Дробный**: 444.5, 295.3, 215.9 |
| `trajectoryTask` | enum | да | VERTICAL (вертикальный участок) / BUILD (набор угла) / HOLD (стабилизация) / DROP (сброс угла) / CORRECTION (коррекция) |
| `maxZenithAngle` | BigDecimal | нет | Максимальный зенитный угол на интервале, °. Отдельное число — по нему AI решает ВЗД vs РУС |
| `drillingConditions` | String (text) | нет | Условия бурения: геология + осложнения (АВПД, осыпи и т.п.), свободный текст. Единое поле — контекст для промпта |

Валидация:
- `depthTo` > `depthFrom`;
- интервалы секций одной скважины не пересекаются;
- соответствие диаметра типу секции автоматически не проверяется — контролирует технолог.

### 6.3. Equipment (справочник оборудования) — таблица `equipment`

Каталог оборудования компании. Заполняется заранее; при генерации Drillix читает его
и вкладывает в промпт; AI возвращает ссылки на позиции. Сама ни на кого не ссылается —
базовая, «нижняя» сущность модели.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | Long | авто | Идентификатор. Именно его AI видит в промпте («#12 …») и возвращает в ответе |
| `type` | enum | да | Категория: BIT (долото) / CALIPER (калибратор) / STABILIZER (стабилизатор) / MOTOR (ВЗД) / RSS (РУС) / MWD (телесистема MWD/LWD) / NMDC (НУБТ) / DC (УБТ) / SUB (переводник). Список расширяемый |
| `name` | String(255) | да | Название/модель («ВЗД Д2-195») |
| `diameter` | BigDecimal | да | Диаметр, мм — **ключ фильтрации** при подборе |
| `description` | String (text) | нет | Свободное описание, включая специфику (вооружение долота, расход/момент ВЗД, резьбы). Передаётся в промпт |

Примечания:
- `type` — не дубликат `name`: name — произвольный текст, на который нельзя опереться
  кодом; type — машиночитаемая категория, на ней держатся проверка ответа AI
  («долото на позиции 1»), группировка в промпте и фильтры в UI.
- Структурированные параметры (расход, момент, вооружение отдельными полями) —
  отложено до появления сценариев использования (фильтры, расчёты) — этап 2.
- Валидация: `diameter` > 0.

### 6.4. Bha (компоновка) — таблица `bha`

Сама сборка — «шапка сметы». Точка сборки: на неё ссылаются элементы (состав)
и рекомендации (обоснования). Налично «тонкая» таблица — это осознанно: её роль —
не хранить данные, а быть объектом, к которому данные привязываются.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | Long | авто | Идентификатор |
| `name` | String(255) | нет | Имя для людей. В MVP пустое (AI имена не придумывает). Этап 2: здесь живут шаблоны КНБК — «Типовая КНБК для кондуктора 444.5, мягкие породы» |
| `createdAt` | LocalDateTime | авто | Дата создания записи |

### 6.5. BhaElement (элемент компоновки) — таблица `bha_elements`

Строка сборки: «что и на какой позиции стоит». Порядок — суть конструкции: один и тот
же набор элементов в разном порядке = разные КНБК с разными характеристиками.

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | Long | авто | Идентификатор |
| `bhaId` | Long, FK → `bha.id` | да | Компоновка, в состав которой входит элемент |
| `orderNo` | Integer | да | Позиция от долота вверх: 1 — долото. Без поля невозможно показать компоновку: в БД у строк нет «своего» порядка |
| `equipmentId` | Long, FK → `equipment.id` | нет* | **Основной режим**: позиция справочника. Все данные элемента берутся из Equipment по ссылке |
| `type` | enum | нет* | **Свободный режим**: категория элемента, когда в справочнике нет подходящей позиции |
| `params` | String (text) | нет* | **Свободный режим**: описание элемента текстом («MWD 172, в справочнике отсутствует») |
| `comment` | String(500) | нет | Комментарий технолога к позиции. От человека, не от AI |

Режимы (пара к трём полям со звёздочкой):
- **основной**: `equipmentId` заполнен → `type`, `params` пустые;
- **свободный**: `equipmentId` пуст → `type` + `params` заполнены. Это способ AI
  сказать «здесь нужно такое-то оборудование, но у вас его нет» — без него пустой
  справочник блокировал бы генерацию целиком.

Валидация:
- ровно один из двух режимов (либо `equipmentId`, либо `type` + `params`);
- `orderNo` уникален в пределах компоновки, от 1 без пропусков;
- долото присутствует и стоит на позиции 1 (проверка ответа AI);
- `params` (от AI) и `comment` (от человека) — разные поля, не смешивать.

### 6.6. BhaRecommendation (AI-рекомендация) — таблица `bha_recommendations`

Мостик «для какой секции → какая компоновка → почему» + чёрный ящик аудита.
Отдельна от Bha осознанно: обоснование принадлежит паре «секция + компоновка», а не
компоновке самой по себе (одну сборку можно рекомендовать для разных секций, для одной
секции — иметь несколько альтернатив, FR-3.3).

| Поле | Тип | Обяз. | Описание |
|---|---|---|---|
| `id` | Long | авто | Идентификатор |
| `sectionId` | Long, FK → `sections.id` | да | Секция, для которой подобрана КНБК. Источник данных промпта |
| `bhaId` | Long, FK → `bha.id` | да | Скомпонованная КНБК — результат генерации |
| `status` | enum | да | DRAFT / APPROVED / REJECTED. В MVP всегда DRAFT (работает как пометка «требует проверки технологом»); полный цикл согласования — этап 2 |
| `justification` | String (text) | да | Обоснование от AI — человекочитаемый кусок ответа |
| `model` | String | да | Модель, сгенерировавшая рекомендацию (аудит: «кто автор»). Нужна, т.к. доступ через Bothub = переключаемые модели; сравнение качества возможно только при записи автора |
| `rawAiResponse` | String (text) | да | Сырой ответ модели до обработки, бит в бит (аудит: «что реально сказано»). justification — цитата, это — оригинал письма целиком; разбор падений парсера — только по сырцу |
| `createdAt` | LocalDateTime | авто | Дата генерации |

### 6.7. Связи между сущностями

#### 6.7.1. Схема связей

```
Well ──1:N──► Section ──1:N──► BhaRecommendation ──N:1──► Bha ──1:N──► BhaElement ──N:1 (опц.)──► Equipment
```

Дерево владения (кто чей «хозяин» через FK):

```
Well (скважина)
 └── Section (секция)                      [Section.wellId]
      └── BhaRecommendation (обоснование)  [BhaRecommendation.sectionId]
           └── Bha (компоновка)            [BhaRecommendation.bhaId]
                └── BhaElement (строки)    [BhaElement.bhaId]
                     └── Equipment         [BhaElement.equipmentId — опционально]
```

#### 6.7.2. Описание связей

| # | Связь | Кардинальность | FK | Смысл и правила |
|---|---|---|---|---|
| 1 | Well → Section | 1:N | `Section.wellId` | У скважины несколько секций; у секции ровно одна скважина. Скважина без секций возможна (только завели) |
| 2 | Section → BhaRecommendation | 1:N | `BhaRecommendation.sectionId` | Для секции — несколько рекомендаций (альтернативы, FR-3.3); рекомендация относится ровно к одной секции. Секция без рекомендаций возможна (ещё не генерировали) |
| 3 | BhaRecommendation → Bha | N:1 | `BhaRecommendation.bhaId` | Рекомендация обосновывает ровно одну компоновку. У компоновки AI-происхождения — ровно одна рекомендация; шаблонная/ручная компоновка (этап 2) может существовать без рекомендаций |
| 4 | Bha → BhaElement | 1:N | `BhaElement.bhaId` | Состав компоновки; элемент принадлежит ровно одной компоновке. Компоновка без элементов нежизнеспособна — минимум один элемент (долото), проверяется при сохранении |
| 5 | BhaElement → Equipment | N:1, **опционально** | `BhaElement.equipmentId` | Основной режим элемента (см. 6.5). Equipment — базовая сущность, сама ни на кого не ссылается |

#### 6.7.3. Правила удаления

| Действие | Поведение системы |
|---|---|
| Удаление Well | Каскад вниз по цепочке: секции → рекомендации → их компоновки → элементы. Пользователь предупреждается |
| Удаление Section | Каскад: рекомендации этой секции + их компоновки + элементы |
| Удаление Bha (вручную, этап 2) | Разрешено, только если на неё нет ссылок из рекомендаций |
| Удаление Equipment | **Запрещено**, если есть ссылки из BhaElement — история рекомендаций не должна терять позиции. Альтернатива удалению — пометка «архив» (этап 2) |

#### 6.7.4. Пример: одна генерация в базе

Секция №5 (кондуктор, долото 444.5) → AI вернула: долото → калибратор → MWD (нет
в справочнике) → УБТ. В базе появляется (жирным — заполненные FK):

```
wells:      id=1, field=«Приобское», wellNumber=«123Г», wellType=HORIZONTAL, …

sections:   id=5, wellId=1, type=CONDUCTOR, depthFrom=30, depthTo=300,
            bitDiameter=444.5, trajectoryTask=VERTICAL, drillingConditions=«мягкие
            терригенные породы»

equipment:  id=12 «Долото III 444.5 СЗ-ГВ»      (лежало, не менялось)
            id=45 «Калибратор 444.5»
            id=78 «УБТ 203»

bha:        id=100

bha_elements:
            (bhaId=100, orderNo=1, equipmentId=12)                    ← основной режим
            (bhaId=100, orderNo=2, equipmentId=45)                    ← основной режим
            (bhaId=100, orderNo=3, type=MWD, params=«MWD 172,         ← свободный режим
                          в справочнике отсутствует»)
            (bhaId=100, orderNo=4, equipmentId=78)                    ← основной режим

bha_recommendations:
            id=7, sectionId=5, bhaId=100, status=DRAFT,
            justification=«Мягкие терригенные породы, вертикальный участок…»,
            model=«gpt-4o-mini», rawAiResponse=«{…сырой JSON…}», createdAt=…
```

Чтение цепочки: рекомендация №7 → для секции №5 → скважины №1; рекомендует компоновку
№100 → из четырёх строк три ссылаются на справочник, одна — свободная (MWD нет
в каталоге, технолог видит пометку).

#### 6.7.5. Общие правила реализации
- Все связи — через `Long id` (внешние ключи).
- В JPA сторона FK описывается `@ManyToOne`; обратные коллекции (`@OneToMany`,
  `mappedBy`) — по необходимости для навигации.

## 7. Интеграция с AI

### 7.1. Провайдер
- Доступ к LLM — через **Bothub** (агрегатор, OpenAI-совместимый API, один ключ
  к моделям разных провайдеров). Конкретная модель — определяется при интеграции,
  не блокер: переключение модели — строка конфигурации.
- Реализация через **Spring AI** (starter model-openai, base-url Bothub; поддержка
  structured output — ответ маппится в Java-класс).
- Опция локальной модели (Ollama) — резерв на случай ограничений конфиденциальности (R2).

### 7.2. Формат взаимодействия
- Системный промпт: роль «опытный технолог по бурению», правила подбора, требование
  отвечать строго JSON-схемой.
- В промпт включаются: параметры секции + оборудование справочника, отфильтрованное
  по диаметру секции и сгруппированное по типам. При росте справочника до больших
  объёмов — RAG (этап 3).
- Пайплайн генерации:
  1. Drillix читает из БД секцию и оборудование нужного диаметра.
  2. Предусловие (fail fast): оборудование есть, иначе — ошибка, AI не вызывается.
  3. Drillix собирает промпт и отправляет в LLM.
  4. Drillix проверяет ответ (FR-3.6).
  5. Drillix сохраняет: Bha + BhaElement + BhaRecommendation
     (status=DRAFT, model, rawAiResponse).
- Валидация ответа на стороне приложения (Jakarta Validation).
- Обработка ошибок: таймауты, ретраи, понятные сообщения об ошибках модели.

### 7.3. Контроль качества
- Все результаты — status=DRAFT с пометкой «предварительно, требует проверки технологом».
- Аудит: по каждой генерации сохраняются модель (`model`) и сырой ответ
  (`rawAiResponse`).

## 8. Нефункциональные требования
- Генерация рекомендации для секции — не более 120 секунд.
- Конфиденциальность: данные буровых программ могут быть коммерческой тайной;
  выбор провайдера — с учётом политики компании; предусмотрена опция локальной LLM.
- REST API задокументирован (Swagger / springdoc-openapi).

## 10. Этапы разработки

**Этап 1 — MVP**
- CRUD скважин и секций (REST + Swagger).
- Справочник оборудования: минимальное наполнение (вручную/скриптом) + просмотр
  с фильтрацией.
- CRUD и импорт справочника.
- Интеграция с LLM через Bothub.
- Генерация, валидация и просмотр КНБК.

**Этап 2**
- Аутентификация (Spring Security).
- Редактирование КНБК, статусы, история, шаблоны КНБК.
- Экспорт.

**Этап 3**
- Загрузка файлов ТЗ (PDF/DOCX) с извлечением параметров.
- RAG по справочнику, регламентам и типовым КНБК.
- Веб-интерфейс.

## 11. Критерии приёмки (MVP)
1. Можно создать скважину и добавить в неё секции с параметрами.
2. Справочник наполняется позициями; при генерации в промпт попадает оборудование
   нужного диаметра.
3. Для секции генерируется КНБК: элементы ссылаются на позиции справочника (или
   помечены как отсутствующие) + обоснование.
4. Некорректный ответ модели (несуществующий equipmentId, невалидный JSON, долото
   не на позиции 1) обнаруживается, наружу — понятная ошибка, приложение не падает.
5. Пустой справочник для диаметра секции → AI не вызывается, понятная ошибка.
6. Результат сохраняется и доступен для повторного просмотра, включая модель и сырой
   ответ (аудит).

## 12. Риски и ограничения
- **R1. Галлюцинации LLM** → обязательная проверка человеком, валидация схемы ответа (FR-3.6).
- **R2. Конфиденциальность** → доступ через агрегатор с учётом политики компании; опция локальной модели.
- **R3. Разнородность форматов ТЗ** → в MVP ручной ввод, парсинг файлов — этап 3.
- **R4. Качество промптов** → итеративная настройка на реальных примерах.
- **R5. Полнота справочника** → качество рекомендаций ограничено наполнением справочника; источник данных определить (раздел 13).
